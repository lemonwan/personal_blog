第 1 站

try-finally 的三大痛点

"面试官问：Java 里关闭资源有几种方式？try-finally 有什么问题？"

在 JDK 7 之前，关闭资源必须手写 try-finally。这段看似简单的代码其实暗藏三个致命问题：

OldWay.java · JDK 7 之前的写法
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("data.txt"));
    return br.readLine();
} catch (IOException e) {
    throw new RuntimeException(e);
} finally {
    if (br != null) {
        try {
            br.close();          // 这里也可能抛异常！
        } catch (IOException e) {
            // 吞掉异常？还是覆盖前面的异常？
        }
    }
}
面试怎么引入？

先从 try-finally 的痛点切入（代码冗长、异常覆盖、资源泄漏），再引出 try-with-resources 的解决方案。面试官会觉得你对底层原理有深入理解，而不只是会写代码。

第 2 站

AutoCloseable 接口：TWR 的契约

try-with-resources 能自动关闭资源的前提是：资源必须实现 AutoCloseable 接口（或其父接口 Closeable）。

AutoCloseable.java · JDK 源码
public interface AutoCloseable {
    // close() 方法声明抛出 Exception（而非 IOException）
    // 子类可以缩小为更具体的异常类型
    void close() throws Exception;
}

AutoCloseable（JDK 7）和 Closeable（JDK 5）的区别：

对比维度AutoCloseableCloseable
引入版本JDK 7JDK 5
close() 声明throws Exceptionthrows IOException
继承关系顶级接口extends AutoCloseable
适用范围所有资源（DB连接、锁等）仅限 I/O 流
幂等性要求不强制规范要求 close() 幂等
CustomResource.java · 自定义 AutoCloseable
public class DbConnection implements AutoCloseable {
    private final Connection conn;

    public DbConnection(String url) throws SQLException {
        this.conn = DriverManager.getConnection(url);
    }

    Connection get() { return conn; }

    // close() 应该是幂等的（多次调用无副作用）
    @Override
    public void close() throws SQLException {
        if (conn != null && !conn.isClosed()) {
            conn.close();
        }
    }
}

// 使用：自动关闭，无需 finally
try (DbConnection db = new DbConnection(url)) {
    db.get().prepareStatement(sql).execute();
}
设计建议

自定义资源的 close() 方法应该是幂等的——多次调用不应抛异常或产生副作用。同时，close() 中的异常应该被记录日志而非静默吞掉。

第 3 站

编译器做了什么？——反编译看真相

"try-with-resources 在字节码层面是怎样的？编译器自动生成了什么代码？"

这是面试中区分"会用"和"理解原理"的关键题。我们来看编译器到底做了什么。

源码：一行简洁的 try-with-resources：

TWR_源码.java
try (BufferedReader br = new BufferedReader(
        new FileReader("data.txt"))) {
    return br.readLine();
}

编译器展开后：等价于一段冗长的 try-finally：

TWR_编译器展开.java · 反编译结果
BufferedReader br = new BufferedReader(
    new FileReader("data.txt"));
Throwable primaryException = null;

try {
    return br.readLine();
} catch (Throwable t) {
    primaryException = t;
    throw t;
} finally {
    if (br != null) {
        if (primaryException != null) {
            try {
                br.close();
            } catch (Throwable suppressed) {
                // 关键：close 的异常被"抑制"而非覆盖
                primaryException.addSuppressed(suppressed);
            }
        } else {
            br.close();  // 正常情况：直接 close
        }
    }
}

核心公式：

TWR 源码 → 编译器生成 try-catch-finally + addSuppressed

开发者看到的是一行代码，编译器生成的是一整套异常安全机制。

第 4 站

异常抑制：被忽略但至关重要的机制

"如果 try 块和 close() 都抛了异常，最终抛出的是哪个？"

这是 TWR 最精妙的设计。在 try-finally 中，finally 的异常会覆盖 try 块的异常，导致丢失真正的错误信息。TWR 用异常抑制解决了这个问题。

SuppressedDemo.java · 异常抑制演示
try (MyResource res = new MyResource()) {
    throw new RuntimeException("业务异常");  // 主异常
}
// MyResource.close() 也抛了 "关闭异常"
// 最终抛出的是 "业务异常"（主异常）
// "关闭异常" 被挂在主异常的 suppressed 列表中
面试高分回答

"try-with-resources 用 addSuppressed() 把 close() 的异常挂在主异常上，而不是覆盖主异常。这样日志中既能看到业务异常，又能通过 getSuppressed() 看到关闭异常，排查问题时信息完整。"

第 5 站

实战模式：TWR 在生产代码中的用法

RealWorldTWR.java · 常见实战场景
// 场景 1：多资源同时管理（逆序关闭）
try (FileInputStream fis = new FileInputStream("in.txt");
     BufferedInputStream bis = new BufferedInputStream(fis);
     FileOutputStream fos = new FileOutputStream("out.txt");
     BufferedOutputStream bos = new BufferedOutputStream(fos)) {
    bis.transferTo(bos);
}
// 关闭顺序：bos → fos → bis → fis（后声明的先关）

// 场景 2：JDBC 事务管理
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql);
     ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {
        process(rs);
    }
}

// 场景 3：JDK 9+ effectively final 变量
BufferedReader br = new BufferedReader(new FileReader("f.txt"));
try (br) {   // JDK 9+：直接用已有变量
    return br.readLine();
}

注意事项：

  • JDK 9 之前，try() 中必须声明新变量；JDK 9+ 支持 effectively final 的局部变量
  • try-with-resources 可以搭配 catch 块，处理资源使用过程中的异常
  • 不要嵌套 try-with-resources（可读性差），应把多个资源写在同一个 try() 中
  • 自定义资源实现 AutoCloseable 时，close() 应该幂等且记录日志
TWR 最佳实践

永远用 try-with-resources 代替 try-finally 管理资源。多资源写在同一个 try() 中，逗号分隔。自定义资源实现 AutoCloseable，close() 幂等。异常抑制机制让排查问题更高效——别忘了 e.getSuppressed()。

第 6 站

总结：try-with-resources 全景回顾

全文核心要点回顾

  • try-finally 三大痛点：代码冗长、异常覆盖、资源泄漏
  • AutoCloseable：TWR 的前提，资源必须实现此接口
  • 编译器展开：自动生成 try-catch-finally + null 检查 + 逆序关闭
  • 异常抑制：close() 的异常通过 addSuppressed() 挂在主异常上，不覆盖
  • 多资源：后声明的先关闭，写在同一个 try() 中
  • JDK 9+：支持 effectively final 变量直接放入 try()
面试 30 秒总结

"try-with-resources 是 JDK 7 引入的资源管理语法糖。编译器在编译期将其展开为 try-catch-finally 结构，自动逆序关闭资源。核心优势是异常抑制机制——close() 的异常通过 addSuppressed() 挂在主异常上，不会像 try-finally 那样覆盖原始异常。前提是资源必须实现 AutoCloseable 接口。JDK 9+ 还支持 effectively final 的局部变量直接放入 try()。"
