第 1 站

从一个根本问题开始

在 Java 中，你从来不需要手动释放内存——JVM 的垃圾回收器（GC）会自动帮你清理不再使用的对象。但你有没有想过：

JVM 怎么知道哪些对象"还在用"，哪些对象"可以删"？

如果判断错了，要么把还在用的对象删了（程序崩溃），要么把不再用的对象留着（内存泄漏）。GC 必须做到精确无误。

这个问题的答案就是 GC Roots 可达性分析算法——现代 JVM（以及 Go、C# 等语言）判定对象存活的基石。面试官经常从这道题切入，一层层深入：

  • GC Roots 具体包括哪些对象？为什么选它们？
  • 可达性分析的完整流程是怎样的？
  • 为什么 Java 不用更简单的"引用计数法"？循环引用问题怎么理解？
  • CMS 和 G1 收集器的"三色标记"是怎么回事？
  • 对象的 finalize() 方法真的能"复活"自己吗？

带着这些问题，我们从 GC Roots 的定义开始。

第 2 站

GC Roots：垃圾回收的"起点集合"

可达性分析的核心思想很朴素：从一组"确定还在用"的对象出发，沿着引用链一路找下去。能找到的都是活的，找不到的就是垃圾。这组"起点对象"就叫 GC Roots。

具体来说，以下 7 类对象可以作为 GC Roots：

类型说明典型例子
栈帧局部变量当前正在执行的方法中，局部变量引用的对象User u = new User() 中的 u 引用的 User 实例
静态变量方法区中类的静态属性引用的对象static Map cache = new HashMap() 中的 cache
常量引用方法区常量池中的引用String 常量池中的字符串对象
JNI 引用Native 方法栈中 JNI 引用的对象C/C++ 代码通过 JNI 回调 Java 时持有的引用
活跃线程当前所有正在运行的 Thread 对象Thread.currentThread() 返回的线程对象
synchronized 持锁对象作为 monitor 锁被持有的对象synchronized(obj) 中的 obj
JVM 内部引用系统类加载器、基本类型的 Class 对象等Integer.class、系统 ClassLoader 实例
为什么选这些对象作为 GC Roots？

这些对象有一个共同特征：它们是程序执行时"天然可达"的入口。

栈帧局部变量代表正在执行的代码直接使用的对象；静态变量是全局可见的；活跃线程是正在运行的执行流；synchronized 持有的对象正在被并发控制使用。如果从这些入口都找不到某个对象，那程序无论如何也不可能再访问到它了——可以安全回收。

第 3 站

可达性分析算法：从根出发的图遍历

可达性分析的算法本质上是对象引用图的遍历。JVM 把所有对象看作图的节点，对象之间的引用关系看作边，然后从 GC Roots 出发做 DFS（深度优先搜索）或 BFS（广度优先搜索）：

为什么必须暂停所有线程（STW）才能做可达性分析？

想象一下：如果分析过程中某个线程把对象 A 的引用从变量 x 转移到了变量 y，而 GC 已经扫过 x 但还没扫 y——它可能误判 A 是不可达的，然后把它回收掉。程序下次访问 A 就会 NPE 或者访问到野指针。

所以传统 GC 必须在安全点暂停所有用户线程（STW），冻结引用关系后再做分析。这也解释了为什么 GC 会造成程序"卡顿"——后续 CMS 和 G1 用三色标记 + 读写屏障来减少 STW 时间。
第 4 站

引用计数 vs 可达性分析：为什么 Java 选了后者？

判断对象是否存活，最直觉的方法是引用计数法——每个对象维护一个计数器，被引用时 +1，引用失效时 -1，归零就回收。Python 和 Swift 就用了这种方式。

但 Java 选择了更复杂的可达性分析，核心原因是引用计数无法解决循环引用：

对比维度引用计数法可达性分析
原理每个对象维护引用计数器，归零即回收从 GC Roots 遍历对象图，不可达即回收
循环引用无法解决，造成内存泄漏天然解决
是否需要 STW不需要（增量式）需要（至少标记阶段需要）
实时性高，引用断开立即回收低，等 GC 触发才回收
实现复杂度低高（需要 OopMap、安全点、写屏障等）
代表语言Python、Swift（配合循环回收器）Java、Go、C#
第 5 站

三色标记：并发 GC 的基石

传统的可达性分析需要 STW（暂停所有线程），停顿时间随堆大小线性增长。CMS 和 G1 收集器为了实现低延迟，引入了三色标记算法，让标记阶段可以与用户线程并发执行。

三色标记的三种状态：

⬜ 白色 — 尚未被 GC 访问过。标记结束后仍为白色 → 垃圾对象
🔲 灰色 — 已被 GC 访问过，但其引用的对象还没全部扫描完
⬛ 黑色 — 已被 GC 访问过，且其所有引用对象都已扫描完毕
并发标记的难题：漏标问题

三色标记允许标记阶段和用户线程并发执行，但这就带来了一个风险：用户线程可能在标记过程中修改引用关系，导致某些存活对象被漏标为白色（误判为垃圾）。

漏标需要同时满足两个条件（Wilson 条件）：

1. 一个黑色对象新增了对白色对象的引用（黑→白）
2. 所有灰色对象到这个白色对象的路径都被断开

CMS 用增量更新（Incremental Update）解决：记录黑色对象新增的引用，在 Remark 阶段重新扫描。
G1 用 SATB（Snapshot-At-The-Beginning）解决：记录被删除的引用，在 Remark 阶段保证这些对象不会被误删。

第 6 站

finalize 复活机制与面试高频题

在可达性分析被判定为"不可达"之后，对象并不是立即被回收。JVM 会给对象一次"自我救赎"的机会——finalize() 方法。

FinalizerDemo.java · finalize 复活示例
public class FinalizerDemo {
    public static FinalizerDemo SAVE_HOOK = null;

    public void isAlive() {
        System.out.println("我还活着!");
    }

    @Override
    protected void finalize() throws Throwable {
        super.finalize();
        System.out.println("finalize() 被调用，尝试自救...");
        // 把自己重新关联到一个 GC Root（静态变量）
        SAVE_HOOK = this;  // ← 复活！
    }

    public static void main(String[] args) throws Exception {
        SAVE_HOOK = new FinalizerDemo();
        SAVE_HOOK = null;  // 断开引用
        System.gc();          // 触发 GC
        Thread.sleep(1000);  // 等 finalize 执行

        if (SAVE_HOOK != null) {
            SAVE_HOOK.isAlive(); // 输出："我还活着!" ← 复活成功
        }

        // 第二次尝试——finalize 只会被调用一次！
        SAVE_HOOK = null;
        System.gc();
        Thread.sleep(1000);
        // 这次 finalize 不会再被调用 → 真正被回收
    }
}
finalize 的复活流程

对象第一次被标记为不可达时，JVM 会检查它是否覆盖了 finalize() 方法且尚未执行过：

1. 如果是 → 放入 F-Queue 队列，由 Finalizer 线程（低优先级）异步执行
2. 在 finalize() 中，对象可以把自己赋值给某个静态变量或栈变量 → 重新关联到 GC Root → 复活
3. finalize() 只会被调用一次。第二次被标记不可达时，直接回收

实际开发中强烈不建议依赖 finalize()：执行时间不确定、可能导致对象复活延迟、性能差。Java 9+ 已将其标记为 @Deprecated，推荐使用 Cleaner 或 try-with-resources。

本篇核心要点
  • GC Roots 是可达性分析的起点：栈帧局部变量、静态变量、常量引用、JNI 引用、活跃线程、synchronized 持锁对象、JVM 内部引用（记忆口诀：栈静常，JNI 线）
  • 可达性分析：从 GC Roots 出发做图遍历，不可达的对象即为垃圾。需要 STW 保证一致性
  • 引用计数法的致命缺陷：循环引用。可达性分析天然解决
  • 三色标记（白/灰/黑）是 CMS/G1 并发标记的基础，通过读写屏障解决漏标问题
  • finalize() 提供一次复活机会，但不推荐使用（@Deprecated since Java 9）

Day 8 — GC Roots 概念

08 GC Roots 概念

📖核心概念：什么是 GC Roots？

在 JVM 的可达性分析算法中，GC Roots 是垃圾回收的起点对象集合。从这些对象出发，通过引用链向下遍历，能够到达的对象标记为存活，不可达的对象则为垃圾。

核心思想

不是孤立地判断对象是否被引用，而是从一组固定的"根"对象出发，看能否找到通往目标对象的路径。

🔒可作为 GC Roots 的对象类型

以下几种对象可以作为 GC Roots：

  • 栈帧中的局部变量表 — 正在执行的方法中的局部变量引用的对象
  • 静态变量引用的对象 — 方法区中类的静态属性引用的对象
  • 常量引用的对象 — 方法区中常量池里的引用（如 String 常量池中的字符串）
  • JNI 引用 — Native 方法栈中 JNI 引用的对象
  • 活跃线程对象 — 当前所有活跃的 Thread 对象
  • 被 synchronized 持有的对象 — 作为 monitor 锁的对象
  • JVM 内部引用 — 系统类加载器、基本类型的 Class 对象、常驻异常对象等

🔬可达性分析算法流程

可达性分析从 GC Roots 出发，采用 BFS/DFS 遍历对象图，标记所有可达对象。未标记的对象即为不可达的垃圾对象。

重要：Stop-The-World

可达性分析必须在 安全点（SafePoint） 执行，此时所有用户线程暂停（STW），才能保证对象引用关系在分析过程中不变。这也是 GC 停顿的主要原因之一。

⚖️引用计数 vs 可达性分析（回顾对比）

对比维度引用计数法可达性分析
原理每个对象维护引用计数器，为0时回收从 GC Roots 遍历对象图，不可达则回收
循环引用无法解决天然解决
效率高，增量式，无需STW需要STW，有停顿
实现复杂度低高（OopMap、安全点）
代表语言Python、SwiftJava、Go、C#
面试重点

两个对象互相引用会被GC回收吗？ 会！可达性分析从 GC Roots 出发，找不到路径就判定为垃圾，循环引用不影响判断。

🎤面试高频问题

  1. GC Roots 具体包含哪些？ — 7类：栈帧局部变量、静态变量、常量引用、JNI引用、活跃线程、synchronized持有对象、JVM内部引用
  2. 为什么选这些对象作为根？ — 它们是程序执行所必需"活的"对象
  3. 什么是不可达对象？ — 从所有GC Roots出发都无法到达的对象
  4. finalize() 复活机制？ — 对象第一次被标记不可达时，若覆盖了finalize()且未执行，进入F-Queue，执行中可重新关联GC Roots"复活"（仅一次）
  5. 三色标记算法？ — CMS/G1并发标记用：白色（未访问）、灰色（已访问未扫完引用）、黑色（全部完成）
记忆口诀

"栈静常，JNI线" — 栈帧局部变量、静态变量、常量池引用、JNI引用、活跃线程
